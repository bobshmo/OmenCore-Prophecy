The unserialised writers were verification and cleaning; both now run inside diagnostic mode, which suspends the keepalive/curve engine, and cleaning restores the preset afterwards. A global gate held across `Task.Delay`-based verification risks a deadlock against the keepalive timer on hardware I can't test. Revisit as the lease coordinator in 4.5. |

Verification deliberately *holds* a level (so its 100% request stays in effect until the caller restores). The static gate (#26) stops a new unpaired Max path being added. **See PR #216**, which closes the remaining hole: the controller is told a direct level is latched, so `RestoreAutoControl` runs its V1 handoff. |

## 3. Corrections to the brief

The brief was written from the public repository plus the supplied changelog. Where it disagreed with the tree:

- `WmiFanController` lives in `src/OmenCore.Core/Hardware/`, not `src/OmenCoreApp/Hardware/`.
- It says the `8DD0` stuck-Max report "lacks live diagnostic evidence". The cause is very likely the verification Max flag (#4 above), found from another board's export (#198).
- It recommends treating a family match as never overriding observed fan count. The tree did exactly that wrong, **unconditionally**, in `CapabilityDetectionService` — the root cause behind three boards (#19). Fixed with an evidence gate rather than a blanket rule: a user-verified entry still wins.
- Its keyboard section assumes unrecognised boards get *no* backend. They get a default four-zone config; the real gap was boards the database *declares* backlight-only (#20).
